# Конфигурация Codefactor для Rust

Выберите профиль и сохраните его в своём проекте. Все YAML самостоятельные: дополнительные файлы для `include` не нужны.

| Профиль | Для чего подходит |
| --- | --- |
| [minimal.yaml](config/minimal.yaml) | Выбрать язык и использовать остальные настройки по умолчанию |
| [medium.yaml](config/medium.yaml) | Задать исключения, основные и структурные пороги, зависимости и кеш |
| [maximum.yaml](config/maximum.yaml) | Настроить дополнительные метрики, слои, наборы и отдельные пороги для участков проекта |
| [axum.yaml](config/axum.yaml) | Веб-сервис на axum или actix-web: исключения `tests/`, `migrations/`, `src/schema.rs`, слои `handlers → services → repositories → domain`, внешние вызовы sqlx, reqwest, redis |
| [workspace.yaml](config/workspace.yaml) | Cargo workspace: слои по крейтам `api → application → infrastructure → domain` в `crates/`, настройки `resolution.rust` |

Профили `minimal`, `medium` и `maximum` не привязаны к фреймворку и подходят любому Cargo-проекту. Профили `axum` и `workspace` берут за основу `medium` и добавляют каталоги, слои, переопределения порогов и внешние вызовы распространённой раскладки; каталог, которого нет в проекте, просто не даёт совпадений.

## Применить профиль

Откройте нужный YAML по ссылке выше и сохраните его как `analyzer.yaml` в корне своего проекта. Cargo устанавливает команды; файлы YAML доступны в репозитории. Команды ниже рассчитаны на установку в `.tools`, описанную в основном README; при установке в `PATH` используйте `codefactor` или `cargo codefactor`.

Из корня анализируемого проекта:

```sh
./.tools/bin/codefactor config check --file analyzer.yaml --strict
./.tools/bin/codefactor scan . --config analyzer.yaml --strict-config
./.tools/bin/codefactor config show --file analyzer.yaml --resolved
```

## Адаптировать под свой проект

- `languages.enabled` определяет языки анализа; пакет поддерживает все пять языков Codefactor.
- `paths.include: ["**"]` включает поддерживаемые файлы, в том числе файлы в корне. Средний и расширенный профили исключают тесты, сгенерированный код и типовые артефакты. Уберите нужные исключения, если хотите анализировать эти файлы.
- Правила `.gitignore` также учитываются. Зависимости выделены через `vendor.paths`, чтобы изучать их связи отдельно от метрик проекта.
- Globs чувствительны к регистру и считаются от корня анализа: `tests/**` исключает только интеграционные тесты крейта. Модульные тесты в `#[cfg(test)] mod tests` остаются в исходниках и попадают в метрики: подавляйте их через `analyzer-ignore` или baseline.
- `limits` задаёт уровни предупреждений `warn` и ошибок `error`. Подберите пороги для своего проекта, затем проверьте их через `config check --strict`. `limits.by_language` нужен только проектам с несколькими языками: для единственного языка он молча перекрывает общий порог.
- Обработчики HTTP принимают экстракторы и состоят из независимых функций, поэтому профили `axum` и `workspace` поднимают для них `function_params` и `lcom4` через `limits.by_path`. `lcom4` считается и для файла со свободными функциями, `types_per_file` учитывает объявления `mod` и блоки `impl`.
- Полное имя сущности для `limits.by_entity` движок строит из пути файла: `src::module::file::Type::method`, для `mod.rs` — `src::module::mod::function`, в workspace — `crates::name::src::lib::Type::method`. Селектор по модулю пишется так же: `mod:src::domain`; `pkg:<имя крейта>` крейты workspace не находит, используйте `dir:crates/<имя>`.
- В расширенном профиле и профилях раскладки пути слоёв, полные имена сущностей, сторонние библиотеки и каталоги старого кода — примеры для замены. `architecture.composition_roots` действует, только если файл сборки попадает в селектор слоя.

Минимальный профиль сохраняет архитектурный и алгоритмический анализ по умолчанию. `scan .` автоматически находит `analyzer.yaml` или `analyzer.yml`; для `scan ./src` передавайте файл явно: `--config analyzer.yaml`. После изменения YAML перезапустите локальный веб-интерфейс.

Добавьте `analyzer.yaml` в репозиторий проекта, а `.analyzer-cache/` — в `.gitignore`.

## Контроль структуры в CI

Архитектурные находки `arch_cycle` и `arch_boundary` не меняют код завершения даже с `--fail-on-warn`. Для блокировки используйте числовые пороги: `limits.module_cycle: {warn: 0}` в `medium`, `axum` и `workspace` превращает цикл между модулями в предупреждение, которое останавливает проверку с `--fail-on-warn`; `{error: 0}` в `maximum` даёт код завершения `2` без флага. Нарушения запрещённых зависимостей между слоями читайте из отчёта `--format sarif` или `--format json`.
