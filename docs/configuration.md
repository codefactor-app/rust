# Codefactor: справочник YAML-конфигурации

Общий формат для PHP, Rust, Python, JavaScript и TypeScript. Все интеграции передают YAML одному движку; секцию `core` дополнительно читает загрузчик пакета. Готовые конфиги находятся в `examples/config` соответствующей интеграции, инструкция — в `examples/README.md`.

Этот справочник одинаков во всех четырёх интеграциях. Исходник для сопровождения хранится в инфраструктурном репозитории: `configuration.md`; `python3 sync-configuration.py` обновляет копии, `python3 sync-configuration.py --check` проверяет их совпадение.

## Быстрый старт и профили

Выберите пример и скопируйте его в `analyzer.yaml` в корне своего проекта. Все примеры самостоятельные, скачивать соседние YAML не нужно.

| Профиль | Содержание |
| --- | --- |
| `minimal.yaml` | Версия формата и один язык; остальные настройки берутся из defaults движка. |
| `medium.yaml` | Область анализа, исключения по соглашениям экосистемы, зависимости, основные и структурные числовые пороги, кеш и вывод. |
| `maximum.yaml` | Расширенные метрики, переопределения, агрегаты, наборы, внешние операции, алгоритмический анализ и архитектурные правила со слоями гексагональной схемы. Для JS/TS и Rust также показаны настройки разрешения импортов. |
| Профили фреймворков | Исключения, слои, запрещённые зависимости, переопределения порогов и внешние вызовы по стандартной раскладке: PHP — `symfony.yaml`, `laravel.yaml`; Python — `django.yaml`, `fastapi.yaml`; Rust — `axum.yaml`, `workspace.yaml`; JS/TS — `nestjs.yaml`, `react.yaml`. |

Профили `minimal`, `medium` и `maximum` не привязаны к фреймворку или CMS. Максимальный профиль показывает возможности настройки: пути слоёв, FQN сущностей, сторонние библиотеки и пороги в нём — примеры, замените их под свой проект. Профили фреймворков берут за основу `medium`; каталог или суффикс файла, которых нет в проекте, просто не дают совпадений. «Минимальный» означает размер конфига: архитектура и алгоритмический анализ по умолчанию включены и в нём.

Запускайте команды из корня анализируемого проекта; замените `codefactor` командой своей интеграции (`./vendor/bin/codefactor`, `npx --no-install codefactor`, `cargo codefactor` или командой из virtualenv).

```sh
codefactor config check --file analyzer.yaml --strict
codefactor config show --file analyzer.yaml --resolved
codefactor config keys
codefactor scan . --config analyzer.yaml --strict-config
codefactor serve . --config analyzer.yaml
```

`scan .` автоматически ищет `analyzer.yaml`, затем `analyzer.yml`, непосредственно в анализируемом каталоге. Поиска вверх по родителям нет. Для `scan ./src` конфиг в корне проекта укажите явно: `--config analyzer.yaml`. Имя `codefactor.yaml` допустимо только при явном указании. `config check` и `config show` по умолчанию читают `analyzer.yaml`; другое имя передавайте через `--file`.

Приоритет: CLI → YAML проекта → defaults. `--strict-config` отклоняет неизвестные ключи; `config check --strict` дополнительно завершает проверку с кодом 3 при любых диагностических сообщениях. Некорректные известные значения диагностируются и заменяются defaults, ошибочные элементы списков пропускаются. Поэтому перед запуском CI используйте именно `config check --strict`. Ошибка синтаксиса корневого YAML также даёт код 3. У `scan` код 2 означает нарушения уровня `error` (либо числовые/алгоритмические предупреждения с `--fail-on-warn`); архитектурные предупреждения на код выхода не влияют.

## Общие правила и include

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `config_version` | Положительное целое; `1` | Версия формата; в примерах используйте `1`. |
| `include` | Строка или список строк; отсутствует | Включить YAML-файл или glob файлов. Допускается в корне, во вложенных отображениях и элементах списков. |

Пути в `include` считаются **от содержащего YAML**, остальные пути и globs — от корня анализа. Абсолютный `cache.path` используется как есть. Для путей используйте `/`, для globs — кавычки, например `"**/tests/**"`. Обнаружение файлов учитывает `.gitignore`; `paths.include` не отменяет его. Настроенные vendor-каталоги дополнительно просматриваются даже при их наличии в `.gitignore`, но общие `paths.include`/`paths.exclude` действуют и на них.

```yaml
config_version: 1
include: ["config/common.yaml", "config/limits/*.yaml"]
limits:
  function_params: {warn: 4, error: 7}
```

Включения применяются по порядку; glob-совпадения сортируются по пути. Отображения сливаются рекурсивно, списки и скаляры заменяются целиком. Ключи рядом с `include` имеют приоритет над включёнными значениями. Лимит глубины — 10; циклы, недоступные и повреждённые включения диагностируются и пропускаются. Пропуск не обязательно останавливает обычный `scan`, поэтому проверяйте конфиг строго.

Пропущенные настройки сохраняют defaults. В частности, `limits: {}` не отключает встроенные пороги. Для необязательных настроек `resolution.rust` значение `null` означает неизвестный вход; в переопределениях алгоритмической сложности `null` означает наследование. Числовые `warn`/`error` не принимают `null`.

## Версия Core для языковых пакетов

```yaml
core:
  version: latest  # либо строка "0.1.3"
```

`core.version` выбирает независимо выпущенный бинарник Core. Допустимы строка `latest` (default) и точная версия `X.Y.Z`. Секция читается только из основного YAML: настройки Core в `include` игнорируются с диагностикой движка. Core распознаёт ключ для проверки конфига, но сам не выполняет скачивания.

Команда пакета `codefactor core update [--config PATH]` скачивает выбранную версию без обновления библиотеки или lock-файла. Она соблюдает закрепление. Без `--config` используются `analyzer.yaml`, затем `analyzer.yml` в текущем каталоге; поиска вверх нет. `CODEFACTOR_CORE_VERSION` переопределяет значение YAML, `CODEFACTOR_BINARY` выбирает свой бинарник и отключает скачивание. Явный бинарник API имеет высший приоритет.

Обновления хранятся в `.codefactor/core/` рядом с основным YAML (без него — в каталоге проекта). Добавьте каталог в `.gitignore`. Кеш общий для четырёх интеграций внутри проекта и изолирован между проектами. Обычный CLI/API не проверяет сеть: отсутствующая закреплённая версия требует явного `core update`. Python wheel и Cargo executable сохраняют встроенный Core как исходный вариант; после установки готового пакета другая версия загружается той же командой.

Строгая проверка YAML с секцией `core` поддерживается новым Core. Для старых релизов задавайте версию через `CODEFACTOR_CORE_VERSION` без этой секции либо запускайте без strict.

## paths, languages и vendor

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `paths.include` | Список glob; `[]` | Пустой список включает все поддерживаемые файлы; иначе файл должен совпасть хотя бы с одним шаблоном. |
| `paths.exclude` | Список glob; `[]` | Исключения имеют приоритет над включением. |
| `languages.enabled` | Список строк; `[]` | Пустой список включает все пять языков. ID: `php`, `rust`, `python`, `javascript`, `typescript`; алиасы `js` и `ts` нормализуются. |
| `languages.extensions` | Отображение расширение → ID; `{}` | Добавить или переопределить расширение без точки: `{phtml: php, pyw: python}`. Язык должен быть разрешён в `enabled`. |
| `vendor.paths` | Список glob; `["vendor/**", "node_modules/**", "target/**", ".venv/**"]` | Пометить зависимости. Список заменяет defaults, а не дополняет их. |
| `vendor.mode` | `collapsed` / `expanded` / `hidden`; `collapsed` | Представление зависимостей в графе: пакеты, подробные узлы или скрытые узлы. |
| `vendor.parse` | `lazy` / `full` / `none`; `lazy` | Разбор при раскрытии, сразу или запрет разбора зависимостей. |

Встроенные расширения: PHP — `php`, `phtml`; Rust — `rs`; Python — `py`, `pyi`; JavaScript — `js`, `jsx`, `mjs`, `cjs`; TypeScript — `ts`, `tsx`, `mts`, `cts`. Краткая форма `languages: [python, typescript]` равнозначна `languages.enabled`. Устаревший корневой `exclude` — алиас `paths.exclude` с диагностикой; в новых конфигах используйте вложенную форму. Vendor не участвует в числовых метриках проекта и архитектурных проверках. При `paths.exclude: ["vendor/**"]` раскрыть этот каталог через `vendor.parse: lazy` нельзя: он уже исключён из области анализа. В `scan` начальный разбор для `lazy` и `none` одинаков: vendor-исходники не разбираются. `lazy` разрешает разбор по запросу раскрытия в `serve`, `none` запрещает его. `full` разбирает доступные vendor-исходники сразу. Метаданные пакетов читаются отдельно от разбора исходников. Посторонние vendor `tsconfig.json`/`jsconfig.json` не обнаруживаются автоматически; явно указанные `extends` и конфиги реально разбираемых vendor-файлов сохраняются и отслеживаются в `--watch`.

## limits: числовые пороги

Порог — отображение `{warn: число, error: число}` с конечными неотрицательными значениями. Можно задать только один уровень. Ключ `enabled: false` выключает правило на этом уровне (общий порог, язык, путь, FQN-шаблон, точная сущность или агрегат), не требуя завышать порог; более позднее переопределение с `enabled: true` включает его обратно и наследует последние `warn`/`error`. Условие срабатывания — строгое **значение > порога**; равенство допустимо. При превышении обоих уровней возвращается `error`.

| Ключ | Default | Назначение |
| --- | --- | --- |
| `limits.<metric>` | См. таблицу ниже | Общие пороги для метрики. |
| `limits.by_language.<language>.<metric>` | `{}` | Переопределение для канонического ID языка. |
| `limits.by_path` | `[]` | Упорядоченный список `{glob: "src/legacy/**", <metric>: {warn: ..., error: ...}}`. |
| `limits.by_entity_glob` | `[]` | Упорядоченный список `{glob: 'App\*View::__construct', <metric>: {warn: ..., error: ...}}` по исходному FQN. |
| `limits.by_entity.<entity>.<metric>` | `{}` | Переопределение для точного имени сущности в отчёте; для функций/классов это FQN. Это не glob и не `class:`-селектор. |
| `limits.aggregates.<metric>.<stat>` | `{}` | Ключ с точками пишется одной YAML-строкой, например `"cyclomatic_complexity.p95"`. |

Переопределения применяются в порядке: общий порог → язык → все совпавшие пути по порядку списка → все совпавшие FQN-шаблоны по порядку списка → точная сущность. `warn` и `error` наследуются независимо; более позднее значение заменяет только заданный уровень. В каждом правиле сохраняйте `warn <= error`. Для агрегатов доступны `avg`, `median`, `max`, `p90`, `p95`; они проверяются у проекта, каталогов и модулей. Переопределения по языку/пути/сущности не меняют агрегатные пороги. `by_entity_glob[].glob` сопоставляется со всем исходным FQN с учётом регистра: `\` — буквальный разделитель PHP namespace, `*` может захватывать несколько разделителей. Для PHP используйте одинарные YAML-кавычки. Последний совпавший шаблон переопределяет только заданные уровни; точный `by_entity` применяется последним. Ошибочные шаблоны, ключи и пороги диагностируются `config check --strict`.

```yaml
limits:
  function_params: {warn: 4, error: 7}
  constructor_params: {warn: 8, error: 12}
  by_language:
    python:
      function_params: {warn: 5}
  by_path:
    - glob: "src/legacy/**"
      function_params: {warn: 6, error: 10}
    - glob: "src/Dto/**"
      lcom4: {enabled: false}
  by_entity_glob:
    - glob: 'App\*View::__construct'
      constructor_params: {warn: 12, error: 24}
  by_entity:
    "app.service.Worker.run":
      function_params: {warn: 7, error: 12}
  aggregates:
    "cyclomatic_complexity.p95": {warn: 12, error: 25}
```

Все встроенные ID метрик (тире означает отсутствие порогов по умолчанию):

| `<metric>` | Измеряется | Default `warn / error` |
| --- | --- | --- |
| `file_lines` | Все строки файла | `400 / 800` |
| `functions_per_file` | Функции файла с учётом `metrics.count_nested_functions` | `20 / 40` |
| `types_per_file` | Типы в файле | — |
| `methods_per_class` | Методы типа с учётом private/accessor-флагов | `15 / 30` |
| `fields_per_class` | Поля типа | — |
| `function_lines` | Строки объявления и тела функции | `40 / 100` |
| `function_body_lines` | Строки тела функции | — |
| `function_params` | Параметры функций и методов, кроме конструкторов, с учётом настроек подсчёта | `4 / 7` |
| `constructor_params` | Параметры конструкторов с теми же настройками подсчёта | `8 / 12` |
| `cyclomatic_complexity` | Цикломатическая сложность | `10 / 20` |
| `cognitive_complexity` | Структурная сложность с учётом вложенности | — |
| `nesting_depth` | Глубина вложенности управляющих конструкций | — |
| `return_points` | Точки возврата функции | — |
| `comment_ratio` | Доля строк комментариев в файле, от 0 до 1 | — |
| `inheritance_depth` | Глубина наследования типа | — |
| `lcom4` | Число несвязанных групп подходящих методов конкретного класса или структуры; ограничения применимости описаны ниже | — |
| `fan_in` | Входящие связи функции в разрешённом графе | — |
| `fan_out` | Исходящие связи функции в разрешённом графе | — |
| `halstead_volume` | Объём Холстеда функции | — |
| `maintainability_index` | Индекс сопровождаемости функции | — |
| `duplicate_functions` | Повторяющиеся токенизированные тела функций, от 30 токенов | — |
| `module_cycle` | Участие в циклах зависимостей модулей; одно нарушение на компоненту | — |

Движок использует **верхнюю** границу для всех числовых метрик. `maintainability_index` и `comment_ratio` обычно интерпретируются с другой стороны; настройка `warn: 20` не означает «предупредить при значении ниже 20». Поэтому примеры не устанавливают для них пороги. `cognitive_complexity` — модель Codefactor, а не контракт совместимости с Sonar.

Конструкторами считаются методы PHP `__construct` (без учёта регистра), Python `__init__`, JavaScript/TypeScript `constructor` и Rust `new`. Для Rust это соглашение об имени фабричного метода; свободная функция `new` остаётся обычной функцией. Вложенные функции конструкторами не считаются. При миграции перенесите переопределения параметров конструкторов из `function_params` в `constructor_params`. Их прежние baseline-отпечатки устаревают; обновите список командой `codefactor baseline update` после проверки новых находок.

LCOM4 не вычисляется для interface, enum, trait, абстрактных типов и типов с менее чем двумя подходящими методами. Статические и абстрактные методы исключаются, включая Python `@staticmethod` и `@classmethod`; конструкторы участвуют, поскольку связывают поля. Если нет ни обращений к полям, ни разрешённых вызовов между подходящими методами этого типа, метрика также отсутствует. Это исключает шум у stateless-сервисов и null-object. Объявленные поля не обязательны: неявные поля Python/JavaScript учитываются по обращениям. Пропущенные типы не добавляют нулевые значения в агрегаты. Старые baseline-записи LCOM4 для таких типов становятся устаревшими.

## metrics и graph

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `metrics.count_implicit_receiver` | bool; `false` | Считать неявный получатель, например Python `self`/`cls`, параметром. |
| `metrics.count_variadic_parameters` | bool; `true` | Каждый объявленный `*args`, `**kwargs`, rest/variadic-параметр даёт один параметр; фактические аргументы вызова не считаются. |
| `metrics.count_private_methods` | bool; `true` | Включать private-методы в `methods_per_class`; для Rust учитывается видимость. |
| `metrics.count_accessors` | bool; `true` | Включать getters/setters и структурные аксессоры в число методов. Одного префикса `get` в имени недостаточно. |
| `metrics.count_nested_functions` | bool; `true` | Включать вложенные функции в `functions_per_file`. Не отключает отдельные метрики этих функций; они не увеличивают число методов содержащего класса. |
| `metrics.histogram_bins` | Положительное целое; `10` | Число интервалов гистограмм агрегатов. |
| `graph.max_implementations` | Положительное целое; `50` | Ограничение числа кандидатов реализации при построении графа. |

## sets: именованные наборы

`sets` — отображение произвольного имени в список селекторов, default `{}`. Селекторы объединяются; `!` исключает совпадения. `set:имя` включает другой набор (также допустимо само имя). Наборы могут пересекаться; неизвестные ссылки и циклы диагностируются при использовании.

```yaml
sets:
  domain: ["dir:src/domain"]
  infrastructure: ["dir:src/infrastructure"]
  application: ["set:domain", "set:infrastructure", "!glob:**/generated/**"]
```

| Селектор | Значение |
| --- | --- |
| `dir:src/domain` | Каталог и потомки по границам компонентов; не совпадает с `src/domainExtra`. |
| `glob:src/**` | Glob пути файла. |
| `file:src/main.rs` | Точный путь файла. |
| `class:App\Service` | Методы типа с указанным FQN. |
| `ns:App\Domain`, `mod:app.domain`, `pkg:crate_name` | Namespace/модуль/пакет и потомки по границам компонентов. |
| `vendor:*` | Vendor-узлы; также можно указать пакет или путь после `vendor:`. |

В WebUI наборы доступны как дополнительная группировка и не заменяют папки и namespace/module. После изменения YAML перезапустите `serve`.

## external: внешние операции

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `external.capture_args` | `none` / `literal`; `literal` | Сохранять первый аргумент вызова, только если он строковый литерал, либо не сохранять. |
| `external.max_arg_length` | Положительное целое; `160` | Максимальная длина захватываемого литерала в символах до редактирования. |
| `external.redact` | Список regex; `[]` | Заменять совпадения в захваченном аргументе на `[REDACTED]`. |
| `external.rules` | Список отображений; `[]` | Пользовательский каталог в дополнение к встроенным языковым правилам. |
| `external.rules[].category` | Строка, обязательна | Категория, например `http`, `db`, `queue`. |
| `external.rules[].pattern` | Строка, обязательна | Имя или glob цели внешнего вызова. |
| `external.rules[].library` | Строка, обязательна | Название библиотеки в графе/отчёте. |
| `external.rules[].operation` | Строка, обязательна | Название операции в графе/отчёте. |
| `external.show_in_hidden_vendor` | bool; `true` | Принимается загрузчиком; в текущем движке отдельное переключение отображения этим ключом не реализовано. |

```yaml
external:
  capture_args: literal
  max_arg_length: 160
  redact: ['(?i)token=[^&\s]+']
  rules:
    - category: http
      pattern: "acme_http.send*"
      library: acme-http
      operation: send
  show_in_hidden_vendor: true
```

Правило классифицирует вызов, а не выполняет его. Вызовы с определением в анализируемом проекте не становятся внешними от одного совпадения имени. Захват аргументов не вычисляет выражения и не раскрывает значения переменных. Regex относится только к захваченным аргументам, а не ко всему исходному коду отчёта.

## resolution: статическое разрешение импортов

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `resolution.node_conditions` | Список строк; `[node]` | Дополнительные условия выбора ветвей `package.json` exports в JS/TS. `import`/`require` и `default` учитываются автоматически. Для browser-проекта можно задать `[browser]`. |
| `resolution.rust.target` | Строка или `null`; `null` | Target triple для вычисления платформенных `cfg`, например `x86_64-unknown-linux-gnu`. Хост анализатора не подставляется. |
| `resolution.rust.features` | Список строк или `null`; `null` | Выбранные features. `[]` — ни одной, `[default]` явно включает локальный default-набор. `null` — неизвестно. |
| `resolution.rust.cfg` | Список строк или `null`; `null` | Дополнительные cfg, например `[test]`. `[]` отключает неуказанные custom/test-флаги; `null` оставляет их неизвестными. |

Читаются `package.json`, `tsconfig.json`/`jsconfig.json` и их `extends`, Cargo manifests и локальные path dependencies; исходники, Cargo и build scripts не выполняются. Node conditions и Rust inputs меняют выбранный граф; метрики исходников по-прежнему описывают найденные файлы. Неизвестные условия и недоступные зависимости отражаются в диагностике разрешения. Для Rust это ограниченная статическая модель локальных features, а не полный Cargo dependency resolver. Не указывайте выдуманные features: используйте объявленные в проекте имена.

## algorithmic_complexity: символьная стоимость

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `algorithmic_complexity.enabled` | bool; `true` | Включить анализ стоимости для всех пяти языков. |
| `algorithmic_complexity.heuristics` | bool; `true` | Разрешить оценки с явно обозначенными допущениями. При `false` требующие их операции получают неизвестную стоимость. |
| `algorithmic_complexity.unknown` | `info` / `warn` / `error`; `info` | Уровень сообщения о неизвестной стоимости. `error` требует полноты анализа, а не доказывает высокую сложность. |
| `algorithmic_complexity.limits.warn` | Строка или `null`; `null` | Символьный порог предупреждения. |
| `algorithmic_complexity.limits.error` | Строка или `null`; `null` | Символьный порог ошибки. |
| `algorithmic_complexity.by_language.<language>` | Отображение; `{}` | Переопределения для канонического ID языка. |
| `algorithmic_complexity.by_path` | Список; `[]` | Отображения с обязательным `glob` и переопределениями. |
| `algorithmic_complexity.by_entity.<FQN>` | Отображение; `{}` | Переопределения для точного FQN функции. |

В каждом переопределении допустимы `enabled`, `heuristics`, `unknown`, `limits.warn`, `limits.error` с теми же типами; пропуск/`null` наследует настройку. Порядок: общая настройка → язык → совпавшие пути по порядку списка → FQN. `by_path[].glob` — glob пути относительно корня анализа.

```yaml
algorithmic_complexity:
  enabled: true
  heuristics: true
  unknown: info
  limits: {warn: "N", error: "N*log(N)"}
  by_language:
    python: {heuristics: true}
  by_path:
    - glob: "src/legacy/**"
      limits: {warn: "N^2", error: "N^3"}
  by_entity:
    "app.service.Worker.run": {unknown: warn}
```

Порог описывает класс роста: `"1"`, `"log(N)"`, `"N"`, `"N*log(N)"`, `"N^2"`, `"N^p*log(N)^q"`, где степени — неотрицательные целые до 128. Кавычки обязательны для константного `"1"`. Это символьные строки, их нельзя помещать в числовой `limits`.

Проверяется асимптотический рост по модели движка. Ошибка превышения требует точного класса (`tight`); верхняя граница (`upper_bound`) и эвристика (`heuristic`) дают предупреждение. Неизвестная стоимость не считается константной или успешно проверенной. Пороги не измеряют миллисекунды и не прогнозируют время выполнения.

## architecture: архитектурные проверки

Архитектура выдаёт `warn`, которые сами по себе не блокируют CI, в том числе с `--fail-on-warn`. Явный режим `scan --compare ... --fail-on-new` отдельно проверяет появление любых новых находок, включая архитектурные. `severity: error` не поддерживается. Чтобы цикл между модулями блокировал CI, задайте числовой порог `limits.module_cycle`: `{warn: 0}` останавливает проверку с `--fail-on-warn`, `{error: 0}` даёт код `2` без флага. Нарушения запрещённых зависимостей между слоями читайте из отчётов `sarif` или `json`. Профиль `strict` проверяет структурные факты; `extended` добавляет экспериментальные рекомендации.

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `architecture.enabled` | bool; `true` | Включить архитектурные рекомендации; числовая метрика `module_cycle` продолжает работать и при `false`. |
| `architecture.profile` | `strict` / `extended`; `strict` | Набор правил. |
| `architecture.exclude` | Список glob; см. ниже | Исключения для архитектуры и `module_cycle`; не отменяют общие `paths`. |
| `architecture.disabled_rules` | Список ID правил; `[]` | Отключить отдельные правила профиля. |
| `architecture.rules` | Отображение ID → параметры; `{}` | Настройки правил из таблицы ниже. |
| `architecture.modules` | Список; `[]` | Явные группы файлов с уникальным непустым `name` и непустым списком `selectors`. |
| `architecture.module_depth` | Отображение язык → положительное целое; `{}` | Максимальная глубина исходных модулей, например `{php: 2, python: 3}`. Явные группы `modules` имеют приоритет. |
| `architecture.modules[].name` | Строка, обязательна | Имя модуля. |
| `architecture.modules[].selectors` | Список строк, обязателен | Объединение по OR: `ns:`, `mod:`, `dir:`, `glob:`, `file:`, `pkg:`. |
| `architecture.layers` | Список; `[]` | Слои с уникальным непустым `name` и непустым списком `selectors`. |
| `architecture.layers[].name` | Строка, обязательна | Имя слоя. |
| `architecture.layers[].selectors` | Список строк, обязателен | Селекторы `dir:`, `glob:`, `ns:`, `pkg:`, `mod:`, `class:`, `file:`. |
| `architecture.forbidden_dependencies` | Список; `[]` | Явно запрещённые направления зависимостей. |
| `architecture.forbidden_dependencies[].from` | Строка, обязательна | Исходный слой. |
| `architecture.forbidden_dependencies[].to` | Строка, обязательна | Целевой слой; должен отличаться от `from`. Оба слоя должны быть объявлены. |
| `architecture.forbidden_dependencies[].principle` | Строка или `null`; `null` | Необязательная метка принципа, например `DIP`. |
| `architecture.composition_roots` | Список селекторов; `[]` | Места сборки приложения, исключаемые из проверки границ слоёв. Допустимы те же селекторы, что у слоёв. |
| `architecture.max_evidence` | Целое 1–500; `50` | Число показываемых диапазонов свидетельств на находку. |

Default `architecture.exclude` (указание своего списка заменяет его целиком):

```yaml
architecture:
  exclude:
    - "**/test/**"
    - "**/tests/**"
    - "**/testing/**"
    - "**/__tests__/**"
    - "**/integration-tests/**"
    - "**/fixtures/**"
    - "**/__fixtures__/**"
    - "**/generated/**"
    - "**/migrations/**"
    - "**/*.test.*"
    - "**/*.spec.*"
```

`architecture.modules` задаёт гранулярность для `module_cycle`, `arch_cycle` и `arch_stability`. Назначение выполняется по файлам: достаточно любого селектора группы. Семантика селекторов совпадает с существующими селекторами наборов. Файл, совпавший с несколькими группами, завершает анализ ошибкой с именами файла и групп; порядок групп не устраняет конфликт. Непокрытые файлы сохраняют исходный модуль, группы без совпадений допустимы, пустой список сохраняет прежнее поведение. Одинаковые имена групп в разных языках не объединяют их; настроенные группы и исходные модули имеют разные внутренние идентификаторы. Группы не меняют исходные FQN, разрешение вызовов, слои или идентификаторы карты кода. В `serve --watch` ошибка назначения сохраняет последний успешный отчёт и показывается в интерфейсе.

```yaml
architecture:
  modules:
    - name: auth
      selectors: ['ns:App\Auth', 'dir:src/LegacySession']
    - name: ranking
      selectors: ['ns:App\Ranking']
```

`architecture.module_depth: {php: 2}` объединяет `App\Billing` и `App\Billing\Store` в исходный модуль `App\Billing`, если файлы не входят в явную группу `modules`. Поддерживаются канонические ключи `php`, `python`, `rust`, `javascript`, `typescript`; глубина — положительное целое. Разделители: `\`, `.`, `::`, `/` соответственно (JavaScript и TypeScript используют `/`). Короткие и пустые модули сохраняются. Настройка применяется к `module_cycle`, `arch_cycle` и `arch_stability`, сохраняя исходные FQN, `file.module`, разрешение вызовов и слои. Изменение участников компонент меняет отпечатки циклов, как и изменение `architecture.modules`; после проверки выполните `baseline update`.

Числовое правило `module_cycle` выдаёт одно нарушение на сильносвязную компоненту модулей. Сначала применяются файловые пороги, подавления и старые файловые baseline-записи, затем оставшиеся нарушения объединяются с максимальным уровнем severity. Исходные числовые метрики файлов сохраняются. Поле JSON `module_cycle` содержит `participants`, полный `files`, замкнутый `cycle.path`, `evidence` и `evidence_total`; `architecture.max_evidence` ограничивает только свидетельства, а поиск и фильтры учитывают все файлы. Новые baseline-отпечатки зависят от отсортированных участников компоненты и severity; прежние файловые записи продолжают действовать. Числовой цикл сохраняет блокирующее поведение при `architecture.enabled: false`.

`architecture.exclude: []` включает тесты в архитектуру, если они не исключены через `paths`. Vendor исключён всегда. Границы слоёв задаются вручную; имена каталогов сами по себе не создают запретов. Пересекающиеся назначения слоям диагностируются. Ссылки `set:` и исключающий `!` для слоёв/composition roots не поддерживаются.

Все правила и допустимые ключи `architecture.rules.<ID>.<параметр>`:

| ID | Профиль | Параметры и defaults |
| --- | --- | --- |
| `arch_cycle` | strict, extended | Циклы зависимостей; настраиваемых параметров нет (`{}`). |
| `arch_boundary` | strict, extended | Запрещённые зависимости между слоями; параметров нет (`{}`). |
| `arch_dry` | strict, extended | `min_tokens: 100`, `min_statements: 5`. Допустимы минимум 30 токенов и 2 оператора. |
| `arch_srp` | extended | `min_methods: 8`, `min_group_methods: 3`. Группы ответственности. |
| `arch_ocp` | extended | `min_sites: 3`, `min_alternatives: 3`. Повторяющийся выбор поведения. |
| `arch_factory` | extended | `min_sites: 2`, `min_alternatives: 3`. Повторяющееся создание объектов. |
| `arch_lsp` | extended | Отказ от унаследованной операции; параметров нет (`{}`). |
| `arch_isp` | extended | `min_methods: 8`, `max_usage_ratio: 0.25`. Раздельные группы потребителей интерфейса. |
| `arch_demeter` | extended | Доступ через промежуточные объекты; параметров нет (`{}`). |
| `arch_stability` | extended | `instability_delta: 0.3`. Направление зависимости по устойчивости. |

Все `min_*` — положительные целые с дополнительными минимумами DRY; `max_usage_ratio` и `instability_delta` — конечные числа от 0 до 1. Параметры одного правила нельзя переносить в другое.

```yaml
architecture:
  profile: extended
  rules:
    arch_dry: {min_tokens: 100, min_statements: 5}
    arch_srp: {min_methods: 8, min_group_methods: 3}
  layers:
    - name: domain
      selectors: ["dir:src/domain"]
    - name: infrastructure
      selectors: ["dir:src/infrastructure"]
  forbidden_dependencies:
    - from: domain
      to: infrastructure
      principle: DIP
  composition_roots: ["file:src/main.rs"]
```

Обычные метрики и связи глубоких PHP-методов, включая длинные цепочки вызовов, вычисляются полностью. Для слишком глубокого тела дополнительная алгоритмическая оценка может иметь статус `unknown`. Подробный экспорт AST имеет отдельное ограничение глубины с диагностикой; оно не исключает функцию из анализа.

## cache и output

| Ключ | Тип / default | Назначение |
| --- | --- | --- |
| `cache.enabled` | bool; `true` | Использовать дисковый кеш исходных моделей. |
| `cache.path` | Строка; `.analyzer-cache` | Каталог относительно корня анализа (или родителя, если анализируется один файл); абсолютные пути разрешены. |
| `output.formats` | Список строк; `[console]` | Форматы вывода по умолчанию: `console` (алиас `text`), `json`, `markdown` (алиас `md`), `sarif`. |

`scan` использует все настроенные форматы, если CLI `--format` их не заменяет. Для файлов задавайте `--out` в CLI; `output.path`/`output.out` отсутствуют. Например: `codefactor scan . --config analyzer.yaml --format json --out report.json`. `metrics` выбирает первый `console`/`json` из списка; AST, граф и другие команды сохраняют собственные форматы экспорта. Для машинного stdout обычно удобнее один формат.

## Подавление отдельных находок

В настоящем комментарии на строке сущности или непосредственно перед ней можно указать `analyzer-ignore: function_params`, другой ID правила или `analyzer-ignore: all`. Текст в строковом литерале не подавляет находки. Подавление относится к конкретной сущности; это директива исходного кода, а не ключ YAML. Для существующего долга также доступен baseline через `codefactor baseline create --root . --config analyzer.yaml`.

Для установленной версии движка окончательный список ключей показывает `codefactor config keys`, а значения после includes и defaults — `codefactor config show --file analyzer.yaml --resolved`. При обновлении сверяйте собственные конфиги строгой проверкой.
