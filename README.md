# Codefactor для Rust

Codefactor — локальный статический анализатор, который помогает находить сложный код, дублирование и проблемы в зависимостях до рефакторинга и ревью. Этот пакет устанавливает консольную команду через Cargo для работы в вашем проекте.

Анализатор поддерживает PHP, Python, Rust, JavaScript и TypeScript: выбор пакета определяет способ установки, а не список доступных языков. Исходный код анализируется локально, не исполняется и не отправляется во внешний сервис.

## Что даёт анализ

| Задача | Что вы получаете |
| --- | --- |
| Найти места для рефакторинга | Размер функций и файлов, число параметров, вложенность, цикломатическая и когнитивная сложность, замечания с файлами и строками |
| Разобраться в незнакомом проекте | Графы вызовов, зависимости между каталогами и модулями, переходы к исходникам в локальном веб-интерфейсе |
| Проверить структуру проекта | Поиск дублирования, циклов зависимостей и нарушений заданных границ архитектурных слоёв |
| Оценить потенциально дорогой код | Статические оценки роста числа операций при увеличении размера входных данных |
| Контролировать изменения | Настраиваемые пороги, отчёты для ревью и CI, baseline для работы с существующими замечаниями |

После `scan` вы видите сводку проекта, метрики и замечания с уровнем, расположением и нарушенным порогом. Это помогает выбрать участок для проверки и сравнивать изменения по одним критериям.

## Установка

Установка напрямую из GitHub не требует регистрации пакета в crates.io. **Пока публичный репозиторий порта пуст, эти команды недоступны:** готовый самостоятельный CLI уже можно скачать из [релизов Codefactor](https://github.com/codefactor-app/core/releases). Инструкции ниже рассчитаны на опубликованный пакет в этом репозитории.

Нужны Rust/Cargo >=1.94, Git и инструменты компиляции для своей ОС. На Debian/Ubuntu также нужны `pkg-config` и `libssl-dev` для HTTPS-загрузки.

Из корня своего проекта установите команды в локальный каталог `.tools`:

```sh
cargo install --git https://github.com/codefactor-app/rust.git --branch main --locked --root ./.tools codefactor
./.tools/bin/codefactor --version
```

На Windows команда находится в `.tools\bin\codefactor.exe`. Добавьте `.tools/` в `.gitignore`; устанавливать Codefactor как зависимость приложения не нужно.

Можно установить команду в обычный каталог Cargo, убрав `--root ./.tools`. Если этот каталог находится в `PATH`, доступны `codefactor` и `cargo codefactor` с одинаковыми аргументами. При установке Cargo компилирует консольную обёртку; сам анализатор скачивается готовым.

При установке выбирается последний стабильный бинарь анализатора из [GitHub Releases](https://github.com/codefactor-app/core/releases), проверяются размер и SHA-256. Поддерживаются Linux, macOS и Windows на x64 и ARM64. Для скачивания нужен доступ к GitHub; токен не требуется. После установки команды работают без сети.

## Быстрый старт

Из корня проекта выполните:

```sh
./.tools/bin/codefactor scan .
```

Для первого запуска конфигурация не нужна. Лучше анализировать корень проекта, чтобы учитывать метаданные импортов и зависимостей, а область анализа ограничивать через YAML.

Чтобы увидеть все замечания и сохранить отчёт:

```sh
./.tools/bin/codefactor scan . --all
./.tools/bin/codefactor scan . --format json --out codefactor-report.json
```

Консоль по умолчанию показывает до 50 замечаний. `--all` снимает это ограничение; экспортируемый JSON всегда содержит полный отчёт. Коды завершения помогают отличить найденные нарушения от сбоя команды — таблица приведена в разделе CI.

## Конфигурация проекта

Создайте `analyzer.yaml` в корне проекта. Например, для Rust:

```yaml
config_version: 1
languages:
  enabled: [rust]
paths:
  include: ["**"]
  exclude:
    - "tests/**"
    - "benches/**"
    - "examples/**"
    - "**/fixtures/**"
    - "**/generated/**"
    - "target/**"
    - "build.rs"
vendor:
  paths: ["vendor/**", "node_modules/**"]
  mode: collapsed
  parse: lazy
limits:
  file_lines: {warn: 400, error: 800}
  function_lines: {warn: 40, error: 100}
  functions_per_file: {warn: 20, error: 40}
  methods_per_class: {warn: 15, error: 30}
  function_params: {warn: 4, error: 7}
  cyclomatic_complexity: {warn: 10, error: 20}
  nesting_depth: {warn: 4, error: 6}
  cognitive_complexity: {warn: 15, error: 30}
  module_cycle: {warn: 0}
architecture:
  enabled: true
  profile: strict
cache:
  enabled: true
  path: .analyzer-cache
output:
  formats: [console]
```

Этот пример не привязан к фреймворку: он анализирует файлы выбранных языков, исключает интеграционные тесты, бенчмарки, примеры Cargo, сгенерированный код и `target/`, задаёт пороги предупреждений `warn` и ошибок `error`. Порог `module_cycle` показывает циклы между модулями, то есть файлами `.rs`. Модульные тесты в `#[cfg(test)] mod tests` остаются внутри исходников и попадают в метрики: используйте `analyzer-ignore` или baseline. Пути считаются от корня анализа, globs чувствительны к регистру. Правила `.gitignore` тоже учитываются; для анализа тестов удалите соответствующие исключения. Каталоги зависимостей отмечены отдельно и могут раскрываться при анализе связей.

Проверьте настройки и выполните анализ:

```sh
./.tools/bin/codefactor config check --file analyzer.yaml --strict
./.tools/bin/codefactor scan . --config analyzer.yaml --strict-config
./.tools/bin/codefactor config show --file analyzer.yaml --resolved
```

`scan .` автоматически находит `analyzer.yaml` или `analyzer.yml`. При анализе другого корня, например `scan ./src`, указывайте файл явно: `--config analyzer.yaml`. Параметры CLI имеют приоритет над YAML, YAML — над настройками по умолчанию.

### Готовые профили

| Профиль | Когда использовать |
| --- | --- |
| [minimal.yaml](examples/config/minimal.yaml) | Выбрать язык и начать с настроек по умолчанию |
| [medium.yaml](examples/config/medium.yaml) | Настроить исключения, основные пороги и кеш для ежедневной работы |
| [maximum.yaml](examples/config/maximum.yaml) | Настроить пороги для разных участков проекта, слои, наборы и расширенный анализ |
| [axum.yaml](examples/config/axum.yaml) | Веб-сервис на axum или actix-web: исключения, слои `handlers → services → repositories → domain`, внешние вызовы sqlx, reqwest, redis |
| [workspace.yaml](examples/config/workspace.yaml) | Cargo workspace: слои по крейтам в `crates/`, настройки `resolution.rust` |

Откройте нужный YAML по ссылке выше и сохраните его в корне своего проекта как `analyzer.yaml`. Cargo устанавливает команды; файлы примеров берите из репозитория.

Каждый пример самодостаточен. Профили `minimal`, `medium` и `maximum` не привязаны к фреймворку; в `maximum` пути слоёв, имена сущностей и каталоги сторонних библиотек служат примерами — замените их на свои. Профили `axum` и `workspace` описывают слои по распространённой раскладке сервиса и workspace и подстраиваются под проект переименованием селекторов. Профиль `minimal` выбирает язык, сохраняя остальные настройки по умолчанию, включая архитектурный и алгоритмический анализ.

[Как выбрать и применить профиль](examples/README.md) · [Полный справочник YAML](docs/configuration.md). Доступные ключи установленной версии также показывает `./.tools/bin/codefactor config keys`.

## Изучение проекта в браузере

```sh
./.tools/bin/codefactor serve . --port 8080 --open --watch
```

Откройте `http://127.0.0.1:8080/`, если браузер не открылся автоматически. В интерфейсе доступны исходники с замечаниями, карта кода, графы вызовов, зависимости, архитектурные проверки и действующие критерии анализа. `--watch` обновляет анализ при изменении исходников; остановка — `Ctrl+C`. После редактирования YAML перезапустите сервер.

Сервер по умолчанию доступен только с этого компьютера. Если меняете `--host`, учитывайте, что подключённые пользователи получают доступ к исходникам анализируемого проекта.

## Полезные команды

```sh
./.tools/bin/codefactor metrics . --group-by directory
./.tools/bin/codefactor relations --a 'dir:src' --b 'dir:tests' --format md
./.tools/bin/codefactor external list --category db
./.tools/bin/codefactor --help
./.tools/bin/codefactor scan --help
```

`metrics` сравнивает показатели по группам; `relations` показывает вызовы между выбранными частями проекта; `external` перечисляет распознанные внешние операции. Замените `src` и `tests` на каталоги своего проекта. Для подробного графа вызовов используйте `./.tools/bin/codefactor graph --help` или откройте нужную функцию в веб-интерфейсе.

## Отчёты и CI

| Формат `scan` | Для чего использовать |
| --- | --- |
| `console` | Чтение результатов в терминале |
| `json` | Сохранение полного отчёта и дальнейшая обработка |
| `md` | Отчёт для ревью и документации |
| `sarif` | Передача замечаний в инструменты статического анализа |

```sh
cargo install --git https://github.com/codefactor-app/rust.git --branch main --locked --force --root ./.tools codefactor
./.tools/bin/codefactor config check --file analyzer.yaml --strict
./.tools/bin/codefactor scan . --strict-config --fail-on-warn --format sarif --out codefactor.sarif
```

Если кешируете `.tools`, проверяйте версию через `./.tools/bin/codefactor --version`: уже установленная команда сама не обновляется. Не переносите установленную команду между разными ОС и архитектурами.

Сохраняйте `codefactor.sarif` как артефакт CI. Для JSON замените формат на `json` и имя файла на `codefactor-report.json`. Логи идут в stderr отдельно от отчёта.

| Код завершения | Значение |
| --- | --- |
| `0` | Нет блокирующих замечаний |
| `1` | Предупреждения при `--fail-on-warn` либо ошибка выполнения команды |
| `2` | Найдены ошибки правил анализа |
| `3` | Синтаксическая ошибка YAML в основном файле конфигурации |

Без `--fail-on-warn` обычные предупреждения не блокируют проверку. Архитектурные замечания носят рекомендательный характер и не меняют код завершения, в том числе с `--fail-on-warn`: нарушения границ слоёв читайте из отчёта `sarif` или `json`. Чтобы цикл между модулями блокировал проверку, задайте порог `limits.module_cycle`: в профилях `medium`, `axum` и `workspace` он даёт предупреждение, в `maximum` — ошибку. При ошибке команды читайте stderr и диагностику отчёта.

### Подключение к существующему проекту

Если в проекте уже много замечаний, после проверки первого отчёта создайте baseline:

```sh
./.tools/bin/codefactor baseline create --root . --config analyzer.yaml
./.tools/bin/codefactor scan . --strict-config --fail-on-warn
```

Baseline сохраняет текущие замечания в `.analyzer-baseline.json` и подавляет их в последующих проверках, чтобы выделить новые. Проверьте файл и закоммитьте вместе с `analyzer.yaml`. В `.gitignore` добавьте `.analyzer-cache/` и создаваемые отчёты.

## Обновление

Версия пакета и версия Core независимы. В основном `analyzer.yaml` можно выбрать последний стабильный Core или закрепить точную версию:

```yaml
core:
  version: latest  # либо "0.1.3"
```

Чтобы скачать выбранный Core без обновления библиотеки и lock-файла:

```sh
cargo codefactor core update
cargo codefactor --version
```

Для другого YAML используйте `cargo codefactor core update --config path/to/analyzer.yaml`. Команда соблюдает закрепление; для смены версии измените конфиг. Переменная `CODEFACTOR_CORE_VERSION=0.1.3` переопределяет YAML, в том числе при исходной сборке Python/Cargo. Версия должна быть строкой `latest` или `X.Y.Z`; диапазоны и префикс `v` не поддерживаются. `core.version` читается только из основного файла, не из `include`.

Бинарники сохраняются в `.codefactor/core/` рядом с выбранным YAML, без конфига — в текущем проекте. Добавьте этот каталог в `.gitignore`. Все четыре интеграции используют один формат кеша; разные проекты обновляются независимо. При обычном запуске CLI/API сетевых проверок нет. Если закреплённой версии ещё нет, выполните `core update`; команда также восстанавливает повреждённый кеш. При неудачном скачивании рабочая версия сохраняется.

`CODEFACTOR_BINARY` и явный путь в API по-прежнему выбирают локальный исполняемый файл. При `CODEFACTOR_BINARY` команда обновления только сообщает о внешнем бинарнике, без скачивания и замены файла. Чтобы запустить старый Core со строгой проверкой YAML, задайте версию через `CODEFACTOR_CORE_VERSION`, не добавляя неизвестную ему секцию `core`.

Готовый Python wheel и Cargo executable содержат исходный Core. После установки выполните `core update` из проекта, чтобы применить его YAML и получить другой бинарник. Пересборка или переустановка пакета для этого не нужна.

## Если что-то не работает

- **Команда не найдена:** при локальной установке используйте `./.tools/bin/codefactor`; для `cargo codefactor` каталог установленных команд должен быть в `PATH`.
- **Ошибка OpenSSL на Linux:** установите `pkg-config` и заголовки OpenSSL, затем повторите установку.
- **Осталась старая версия:** выполните `cargo codefactor core update`.
- **Ошибка HTTPS:** проверьте доступ к GitHub и доверенные сертификаты.
- **Настройки не применяются:** запускайте из корня проекта или передайте `--config analyzer.yaml`; используйте `config check --strict` и `config show --resolved`.
- **Нужна установка через корпоративное зеркало:** `CODEFACTOR_RELEASE_BASE_URL` задаёт HTTPS-адрес зеркала, `CODEFACTOR_CA_BUNDLE` — доверенный сертификат. `CODEFACTOR_BINARY` позволяет использовать уже скачанный бинарь нужной платформы вместо сетевой загрузки.

## Как читать результаты

Статический анализ может не определить часть динамических вызовов, рефлексии и метапрограммирования. Оценки алгоритмической сложности описывают рост числа операций, а не измеренное время выполнения. Проверяйте диагностику разбора и определения связей; отсутствие замечания не доказывает отсутствие проблемы. Дополнительные архитектурные гипотезы профиля `extended` требуют проверки человеком.
